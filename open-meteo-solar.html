The problem

Solar output chases the sun, and clouds move fast

A passing cloud can swing a plant's output within minutes. That makes the forecasting window unusually tight.

Fast, cloud-driven swings

Because power tracks sunlight, cover that rolls in and out reshapes output on a scale of minutes.

Deviations cost money

Grid operators need your output committed in advance. Missing what you promised carries a real penalty.

The next few hours

Not tomorrow. The useful question is what the sky over this site will do later today.

The awkward middle window

Conditions shift too quickly for a comfortable answer, yet day-ahead forecasts are too broad to help. The value sits in that gap.

What it is

One query interface over ~30 weather models

Open-Meteo is a free weather API that puts national providers (ECMWF, NOAA, Germany's DWD, Météo-France and others) behind a single interface. Pick a model, or let it choose one for your location.

Where the data comes from

Two very different sources

One predicts the sky; the other measures the light that already arrived. Knowing which you're holding is half the battle.

Weather models

~30 · forecast

Run by national agencies, they forecast what the sky will do: the predictive side of the pipeline.

Satellites

7 datasets · measured
  • Measure the irradiance that has already arrived, including a blended product.
  • Himawari (Asia-Pacific), EUMETSAT MSG & IODC (Europe, Africa, India), DWD MTG, and SARAH3, whose record runs back to 1983.

North America is the gap

The GOES satellites aren't integrated yet, so satellite irradiance coverage there is missing for now.

Method

How we tested which variables actually help

The goal: find which weather variables measurably improve a solar-power forecast a few hours ahead.

1

Inventory

Check every model and variable: whether it returns data for the sites in question, and how far back that data actually goes.

2

Reconstruct

Pull each forecast as it was issued ahead of time: the value that was genuinely known then, not a later revision.

3

Correlate

Join those forecasts to measured power output and measure which variables actually track it.

Daytime hours only: easy to get wrong

Output is zero at night by definition. Leave night in and every sun-related variable looks predictive, because both sides sit at zero together for half the day. It inflates results and means nothing.

The key insight

Reconstruct the forecast that was actually available

Append _previous_dayN to any variable and you get its value as predicted N days before it was valid, for N from one to seven.

That makes an honest backtest possible: each training point reflects what was genuinely known at the time, rather than a later revision.

Rare among weather APIs

Many providers simply don't expose this kind of historical-forecast data at all.

previous_runs.py
params = {
    "latitude": lat,
    "longitude": lon,
    # forecast as issued a day earlier
    # not a later revision
    "hourly": "shortwave_radiation_previous_day1",
    "start_date": start,
    "end_date": end,
    "timezone": "UTC",
}

Resolution & cadence

How fine is the data, really?

A smaller grid cell means more spatial detail. Where a regional model exists, resolution jumps sharply.

10–25 km
Global models
IFS 0.25°, ICON Global 11 km, GFS 13 km.
~5 km
Satellite
Mostly 0.05°; DWD MTG at 0.025°. Steps 10–30 min.
2–3 km
Regional models
ICON-D2 ~2 km (DE), HRRR 3 km (US), AROME 2.5 km (FR).

Hourly by default

A minutely_15 option exists, but it only adds real detail where a regional model is available; elsewhere it's just interpolated hourly data.

Outside regional domains

Across much of Asia, Africa, South America, the Middle East and Australia, you generally rely on global models.

Results

Irradiance leads. Then a few others.

Each variable was tested individually against solar output: relative strength, in one climate.

Irradiance: GHI, GTI, direct, diffuse, DNIcore signal · strongest
Sunshine durationhow much of the hour was sunny
Humidity & vapor-pressure deficitstrongest non-radiation signal
Reference evapotranspirationsurprising, but derived from radiation

The method travels; the results may not

Higher humidity generally meant lower output (likely cloudier). Evapotranspiration is built from radiation, temp and humidity, so it may just carry the solar signal. Tested one climate, one variable at a time. Always test with your own data, and start with irradiance.

Pitfall 01

The archive that isn't a forecast

For training, you need the forecast that would have been available then, not a better estimate assembled with hindsight. Three common traps:

Reanalysis (e.g. ERA5)

Built from observations collected after the fact, not what a forecast model would have known at the time.

"Historical Forecast" API

Looks the part, but stitches early hours from different runs, closer to actual conditions than a true forecast.

Current-only forecasts

Asking for a past date returns the latest run, not the forecast that was available on that date.

The fix

Open-Meteo's Single Runs API is built for backtesting without look-ahead bias. Always ask: does this reflect what was actually known at the time?

Pitfall 02

Averaged is not the same as instantaneous

Some variables are an average over the previous hour; others are the value at that exact instant. Mix them up and features quietly shift by 30 minutes.

The consequence

Apply the same time adjustment to both types and some features end up shifted by half an hour.

The fix

Check whether each variable is an hourly average or an instantaneous value before aligning it to your target.

Pitfall 03

Documented coverage is a hypothesis

The published archive dates didn't always match what the API returned, and coverage varied by variable, not just by model.

Coverage varies by variable

A model might carry temperature from an earlier date but radiation only from much later. Don't assume one start date covers everything.

A sanity check that paid off

Radiation and output should track each other closely. Our first run showed almost none. Code ran fine, data looked valid. The culprit was a timezone bug.

The fix

Verify the actual coverage for the variables you need. And don't just check that data looks valid; check that it makes sense.

Takeaways

Five checks before you build

Reconstruct, don't just fetch

Confirm you can rebuild past forecasts as they were issued, not only access current ones.

Verify coverage

Treat documented dates as a starting point, then check what the API actually returns.

Average or instant?

Know which each variable is, and align them to your target accordingly.

Keep a sanity check

Hold onto a relationship you expect to be true, and re-run it after every pipeline change.

Start with irradiance

It's the strongest signal. Add other variables only once your own data shows they help.

Bottom line

A great free tool for prototyping, if you read carefully

Most of the friction we hit wasn't bugs. The information was usually documented, just scattered across different pages. Know what to check going in, and Open-Meteo is a genuinely useful starting point for solar work.
